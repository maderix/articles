Parts 1, 2, and 3 of this series treated the ANE as a tool. We compiled models to it, measured how fast they ran, and trained a transformer on it. But we never described the machine itself. What is the ANE as a piece of silicon? How is it organized? What can it compute, and why does it behave the way we measured?

Most of what follows is our own reverse engineering on an M4, done across Parts 1–3 and the months since: the private API surface below CoreML and the in-memory compile path; the compiled program format (a Mach-O with magic 0xBEEFFACE) decoded down to individual field offsets, tiling formulas, and the activation lookup table; from-scratch emitters that produce byte-identical binaries and run at 98.8% of peak without Apple's compiler; the evaluation path traced through the framework's vtable to the kernel; the int8, geometry, dispatch-floor, TD-count, and compute/DMA-overlap measurements; and a 2,360-byte hardware parameter table pulled out of the live compiler with a debugger. Where we lean on someone else, it is named: Bryngelson's 302-page reference (A11 through M5, with the M1 compiler decompiled) supplies the compiler's internal pass names and the field naming for that parameter table, and the Orion paper catalogs MIL-level constraints for LLM work. Some numbers in Parts 1 and 2 were wrong; the corrections are marked inline.

What the ANE Is

The Apple Neural Engine is a fixed-function matrix accelerator built into every Apple system-on-chip since the A11 (2017). It sits on the same die as the CPU and GPU, shares the same unified DRAM, and draws from the same power budget. Apple builds it in volume and documents almost none of it. There is no public instruction set, no driver interface, no way to confirm a computation ran on it. The public API is CoreML, where the engine is one placement option behind an opaque scheduler.

What the three engines have in common is the memory, not the programming model. A tensor produced by the GPU can be handed to the ANE by mapping the same IOSurface; the cost the ANE adds is a fixed ≈90 µs per submission.

The ANE is not a general-purpose processor. It has no instruction pointer in the traditional sense, no branch instructions, no loops, no dynamic control flow. You submit a compiled graph and the engine runs the entire thing as one atomic operation. You cannot pause it, step through layers, or inspect intermediate values. Input and output happen through IOSurfaces (shared memory regions that the CPU, GPU, and ANE can all access without copying).

On M4, the ANE has an internal codename of H16G. The IORegistry identifies it as AppleH16ANEInterface with architecture h16g, version 192, and 16 registered cores. Previous generations: H11 (A11), H13 (M1), H14 (M2), H15 (M3). The "G" suffix likely indicates the Mac/iPad class (as opposed to phone or watch variants).

Inside the Engine

Our picture of the engine's internals comes from three directions. From the outside: hundreds of compiled programs diffed byte by byte, which is how the task-descriptor fields, the tiling rule, the weight-streaming stride, and the lookup-table format were recovered, each confirmed by emitting binaries from scratch and running them. From the compiler: a 2,360-byte parameter table (the Hardware Abstraction Table, or HAT) that we pulled out of the live M4 compiler process with LLDB by calling ZinIrHalH16g::GetParams(); it holds every number the scheduler reads. And from the Bryngelson decompilation of the M1 compiler, which gave us the names of the internal passes and the meaning of the HAT's fields so the M4 values could be read rather than guessed. Every number below is an M4 reading unless it says M1.

The compiler's memory decision in one picture. Below 2 MiB per operand the load and the compute serialize; above it the operand is tiled and the DMA of the next tile hides under the current tile's compute. The measured throughput step at ~2.3 MiB on M1 is this crossing, and the M4 HAT carries the same threshold.

SRAM

The on-chip memory is a 64-bank scratchpad with a 16-byte interleave granule. An address maps to bank floor(addr / 16) mod 64. The compiler manages it as scratch space with no runtime cache replacement policy. When a tensor's data fits in SRAM, it stays there for the duration of the computation. When it does not fit, the compiler tiles the work and streams data through in chunks.

The streaming threshold is 2 MiB per operand (not per operation, and not a sum of all operands). This value comes from the HAT at offset 0x1b8 and is the same on M1 and M4. Below 2 MiB, an operand can be fully resident before compute starts. Above it, the compiler splits the operand into tiles and double-buffers them: while tile N computes, tile N+1 loads.

In Part 2 we measured a throughput cliff around 24-32 MB and attributed it to total SRAM size. The HAT tells a more precise story: the 2 MiB boundary is where the compiler switches from resident to streamed mode for each operand. Performance above that boundary depends on how well the DMA engine can overlap tile loads with compute, not on a hard capacity wall.

Weights have their own budget. Up to 64 KiB of weights stay resident on-chip (the "kernel-coefficient store"). Weights up to 16 MiB can be streamed through in 16 DMA chunks. The compiler divides the weight matrix into 16 pieces regardless of total size and loads them sequentially.

Finding. One number, HAT[0x1b8] = 2 MiB per operand, decides whether the compiler keeps an operand resident or tiles and streams it. It is the same on M1 and M4.

Compute

The M4 compute array has 8 compute sets. Each compute set has 8 accumulators. Products are fp16. The accumulator itself is wider (likely fp32-class, based on M1 analysis), and the final output is rounded back to fp16. This means the ANE does not have native int8 multiply-accumulate. Int8 weights are dequantized to fp16 before the MACs fire. The "38 TOPS int8" marketing number counts each fp16 MAC as two int8 operations.

The M1 had 4 compute sets. The doubling to 8 on M4 is consistent with the ~1.6x throughput increase between generations (M1: ~12 TFLOPS, M4: ~19 TFLOPS). The remaining gap may come from higher clock frequency on M4, but the ANE frequency has not been measured directly on either chip.

The compiler controls the output-channel-group (OCG) size, meaning how many output channels are computed in one pass through the accumulator. The OCG is the smaller of a power-of-two accumulator budget and a format-specific byte cap (32, 16, or 8 bytes depending on weight format). The OCG formula and its constants are identical on M1 and M4.

Finding. The multipliers are fp16. Int8 is dequantized before them, so "38 TOPS" is 19 TFLOPS counted twice. M4 doubled the compute sets (4 → 8), not the lane width.

DMA

Data moves between DRAM and SRAM through DMA engines. The M1 compiler exposed three tile-DMA engines plus a kernel-DMA engine. The M4 DMA engine count has not been directly measured. In our tests, sweeping 2 through 8 independent input planes produced a linear slowdown of ~995 µs per additional plane. No concurrency knee appeared, suggesting the DMA path serializes tile loads in the configurations we tested.

Fused operations avoid the DMA round-trip entirely. When consecutive operations in a compiled graph feed into each other, the compiler marks the intermediate as DMA_INTER instead of DMA_STORE + DMA_LOAD. The data stays in SRAM. This is the single largest optimization the compiler makes: a fused matmul + bias + relu runs 5.7x faster than dispatching the three ops separately. The compute is identical. The saved DRAM round-trips are the entire difference.

Finding. Fusion is the compiler's biggest lever: DMA_INTER keeps intermediates in SRAM. matmul + bias + relu fused runs 5.7× faster than the same three ops dispatched one at a time.

What the ANE Computes

The ANE supports approximately 50 hardware layer types, verified through the ANECompiler.framework validator exports (_ANECValidate*Layer). In practice, the operations that compile and execute fall into five groups.

GroupOperations
Matrix opsmatmul, conv (1x1/3x3/5x5), depthwise conv, SDPA (fused attention)
Elementwise256 ALU opcodes: add, mul, sub, max, min, plus post-ops (square, sign). Controlled by a single opcode byte in the binary.
Activationsrelu (direct ALU), sigmoid, tanh, gelu, silu, exp, softplus, elu (via 33-point piecewise-linear LUT), rsqrt/sqrt/reciprocal (dedicated hardware)
Reductionsreduce_sum, reduce_mean, reduce_max (native hardware, not conv trick), softmax and layer_norm (decomposed into 6-7 fused primitives)
Layoutreshape, transpose, concat, space_to_depth, depth_to_space, slice

Operations not supported on the hardware: acos, asin, tan, log, cumsum, mod, and boolean logical ops. These fall back to the CPU (via BNNS) or GPU (via Metal). CoreML handles the segmentation automatically.

Activations like sigmoid and gelu do not have dedicated hardware. Instead, the compiler stores 33 fp16 samples in a segment called __KERN_0 and the hardware linearly interpolates between them at evaluation time. For sigmoid with samples from -8 to +8, the max error is 2.4e-4. We verified that replacing the samples with an arbitrary function (x³, not a MIL op) produces correct output on hardware. Any pointwise function approximable by 33 piecewise-linear segments over a fixed domain can run on the ANE.

How Programs Reach the Hardware

The path from a neural network description to hardware execution has five layers:

MIL text (typed SSA graph)
  → ANECCompile() via XPC to ANECompilerService
    → 0xBEEFFACE Mach-O binary (Task Descriptor stream)
      → aned daemon cache → IOKit DMA → ANE SRAM
        → atomic graph execution → IOSurface output

MIL (Machine Learning Intermediate Language) is the input format. It is a text-based SSA language with typed tensors, named operations, and explicit shapes. The ANE compiler is a C function (ANECCompile) in the private ANECompiler.framework. It can also be reached through the ObjC API (_ANEInMemoryModel.compileWithQoS:).

The compiler produces a custom Mach-O binary with magic number 0xBEEFFACE, CPU type 0x80 (128, for ANE), and CPU subtype 0x07 (H16G). The binary contains a stream of Task Descriptors (TDs) that configure DMA engines and the compute array. The program is not a sequence of instructions in the CPU sense. It is a register-write stream that configures the hardware for one graph execution.

Dispatch from the host goes through the aned daemon via XPC for compile and load, but evaluation takes a direct path through ANEServicesProgramProcessRequestDirect without the daemon. The host posts a mailbox command, the engine runs the entire graph, and the output appears in the designated IOSurface.

Every evaluation, regardless of computation size, costs approximately 90 µs of host time (XPC round-trip + IOKit setup). This floor is CPU-bound and does not change with SoC power state. Any operation completing in under ~1 ms spends a large fraction of wall-clock time in dispatch overhead. This is why operation fusion matters so much: fewer dispatches per forward pass means less time in the 90 µs tax.

Finding. Every evaluation costs ≈90 µs of host time before the engine does anything. Under ~1 ms of work, dispatch dominates; the fix is fewer, larger programs.

Performance

Corrections from Parts 1 and 2: The power figure of 2.79 W and efficiency of 6.6 TFLOPS/W reported in Part 2 do not reproduce. Those measurements were taken with pmset lowpowermode enabled without our knowledge (it persists across reboots). The corrected M4 peak power is 4.57 W at fp16 peak, giving 4.1 TFLOPS/W. All numbers below use the corrected measurements from August 2026.

Throughput

Peak throughput requires deep operation chains (32-64 layers) at the right channel/spatial balance (512-1024 channels, 64²-128² spatial). A single matmul uses roughly 30% of peak because the 8-core pipeline is not fully occupied. A 64-layer conv1x1 chain fills the pipeline and reaches 98.8%.

One matmul, however large, leaves two thirds of the array idle. A chain of 32 or more conv1x1 layers at 512–1024 channels fills the pipeline and runs within 1.2% of the ceiling.

The hardware ceiling is 19 TFLOPS fp16. Apple markets the ANE as "38 TOPS" by counting each fp16 MAC as two int8 operations.

INT8: activations, not weights

Correction from Part 2: Part 2 reported that int8 quantized models run at the same throughput as fp16 and concluded the ANE dequantizes int8 to fp16. This is half right. Int8 weights buy nothing (1.00x). The speedup comes from int8 activations, controlled by a single DMA configuration bit that tells the engine to move inter-tile data as 1 byte instead of 2. Int8 activation quantization gives 1.85x throughput.

WeightsActivationsSpeedup

int8fp161.00x
int8int81.85x

Quantizing the weights alone changes nothing the multiplier can see. Quantizing the activations halves every transfer between tiles, and on a 128-layer chain that is the whole 1.85×.

Finding. Int8 weights: 1.00×. Int8 activations: 1.85×. The speedup is one DMA bit that halves inter-tile traffic; the MACs never see int8.

The ANE has hard power gating: exactly 0 mW at idle, instant on. FP16 is the more power-efficient mode per operation. W8A8 draws 2.7x the power for 1.9x the throughput. Int8 activations buy throughput and SRAM footprint, not energy efficiency.

Geometry matters

A shallow-channel tensor starves the compute array. Reshaping with SpaceToDepth into the 512-1024 channel band, computing there, and reshaping back with DepthToSpace is the biggest performance lever available:

Pipeline (32 layers)FP16 TFLOPSW8A8 TOPS
Native 64ch 128²3.926.62
S2D(4) → 1024ch 32² → D2S16.3731.97
Speedup4.18x4.83x

The array parallelizes over output channels. A shallow tensor leaves most compute sets idle regardless of how large its spatial extent is; folding spatial into channels with SpaceToDepth is the single biggest lever we found.

S2D/D2S overhead is 0.3-1.4% of the pipeline. Avoid block_size=2: the compiler lowers it as a convolution with one-hot weights (2.8-3.1% overhead) rather than a DMA reshuffle.

Finding. The array parallelizes over channels. SpaceToDepth(4) on a 64-channel tensor lifted a 32-layer chain from 3.92 to 16.37 TFLOPS, 4.18× end to end.

ANE vs GPU vs CPU

The three engines on an M4 serve different roles. None replaces the others.

For supported operations at batch sizes large enough to amortize the 90 µs dispatch, the ANE is 5x faster than the GPU and 8-13x more power-efficient than the CPU. The GPU wins on flexibility and zero dispatch overhead for in-flight work. The CPU wins on arbitrary code and instant dispatch.

A model, not a measurement, except for its two inputs: the ≈90 µs floor measured on M4 and the ≈4.9× peak ratio between the ANE and the CPU's matrix unit. Anything shorter than ~23 µs of ANE work is faster on the CPU; anything longer belongs on the ANE, and fusing ops into one program moves work rightward.

For LLM inference, the practical split is: ANE for prefill (large-batch matrix operations, tiled as convolutions), CPU/SME for token-by-token decode (single-token operations where the 90 µs dispatch dominates). For on-device training, the ANE handles forward and backward matmuls at 2.8-4.6 W while the CPU handles weight updates and operations the ANE does not support (masked attention, Adam optimizer).

Finding. ANE for prefill and anything over ~25 µs of matrix work; CPU/SME for single-token decode where the 90 µs floor would dominate.

The M6: Dual ANE

Apple announced the M6 on August 25, 2026, built on TSMC's 2nm process. The headline change for the ANE: the M6 has two of them. Apple calls it a "Dual 16-core Neural Engine" and claims 2x peak compute over previous generations. System frameworks can use both engines simultaneously.

Apple did not publish a TOPS number for the M6 ANE. Based on what we know: if each engine matches the M4's 19 TFLOPS fp16, the dual configuration would deliver 38 TFLOPS fp16 (76 TOPS by Apple's int8 marketing math). Whether the two engines share SRAM, coordinate DMA, or simply operate as independent units with separate memory pools is not disclosed. The DRAM bandwidth increased to 170 GB/s (from 120 GB/s on M4), a 42% increase that would partially offset the bandwidth pressure of running two engines against the same memory.

What Apple has said about the M6 Neural Engine fits in one box: two of them, twice the peak, both usable at once by system frameworks. The dashed link and the three questions under it are what a HAT dump and a dispatch-floor measurement on real hardware would settle.

Several architectural questions follow from the dual-engine design. Can a single compiled graph span both engines, or does the framework partition the model into two independent subgraphs? Does each engine have its own 2 MiB operand threshold and 64 KiB kernel store, or do they share? Are the dispatch XPC paths independent (two 90 µs tax rounds, or one)?

Apple also added "Neural Accelerators" to the M6 GPU cores, claiming a 30% improvement over M5 for GPU-side AI work. These are separate from the ANE and appear to be small fixed-function units within the GPU pipeline, similar to NVIDIA's tensor cores. Whether they share the same ISA as the ANE or use their own encoding is unknown.

The M6 skipped Pro and Max variants. Apple says it is focusing on "future AI-centric chip designs." The dual-ANE M6 may be the beginning of a scaling strategy where NPU count grows with die area, the way GPU cores have scaled across the M-series lineup. If so, the M6 Pro/Max equivalents (whenever they arrive) could have 4 or 8 ANE instances.

We do not have an M6 to test. The predictions here are extrapolations from M4 measurements and Apple's public statements. When an M6 is available, the first experiments would be: dump the HAT to check whether the per-engine parameters changed, measure the dispatch floor for single and dual-engine workloads, and determine whether the two engines can overlap or must serialize.

Finding. M6 ships two 16-core engines and a 42% wider memory bus. Apple has said "2× peak" and nothing about how they coordinate.

Limits and Open Questions

Program size. 256 Task Descriptor blocks execute correctly on M4. 257 fails with status 0x15. But the failing case also crosses exactly 512 MiB per tensor, so the boundary could be either limit or both.

No compute/DMA overlap. A combined matmul + ReLU program ran only ~1% faster than the sum of the two run separately (after subtracting the dispatch floor). The engine appears to serialize MAC and DMA work within a single program.

No wide issue. Eight independent adds were 1.008x faster than eight chained adds. The engine does not execute independent operations in parallel across compute sets in the configurations we tested. The M1 compiler permits MAC + planar-engine co-issue for independent operations on different engine types, but same-engine overlap is rejected.

No FP8. The E4M3 capability gate in the HAT is zero on both M1 and M4. The compute path is fp16.

No branching. The ANE has no conditional execution. Every operation in a compiled graph runs every time. Dynamic shapes are supported only through procedure indices (selecting among pre-compiled shapes) or runtime-variable dimension bindings in the dispatch descriptor.

Unknown lane width. The M1 paper reports 4 fp16 or 8 int8 output channels per cycle. The M4 HAT carries the same per-accumulator tier values (8/4/2/1) but these are tiling-formula inputs, not the per-cycle rate itself. The M4 per-cycle lane width has not been independently measured.

The M4 ANE is a fixed-function fp16 matrix accelerator with 8 compute sets, 64 banks of on-chip SRAM, and a compiler-managed streaming model that tiles work around a 2 MiB per-operand budget. It reaches 19 TFLOPS fp16 at under 5 watts and draws exactly 0 mW when idle. Its constraints (no branching, fixed op set, fp16-only MACs, 90 µs dispatch floor) are the price of that efficiency. The hardware is not complicated. The complexity is in the software stack above it, which Apple chose to keep private.

The M6 doubles the engine count. Whether that is two independent accelerators or a coordinated pair remains to be measured.
